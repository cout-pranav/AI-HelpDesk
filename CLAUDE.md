```
dotnet build                       # build
dotnet run --launch-profile http   # run at http://localhost:5280 (applies migrations + seeds admin on startup)
dotnet ef migrations add <Name>    # new migration (dotnet-ef installed globally); applied automatically on next run

# Admin seed credentials (one-time setup), stored in the user-secrets secrets.json, read on startup.
# Env var equivalents outside Development: SeedAdmin__Email / SeedAdmin__Password / SeedAdmin__DisplayName.

dotnet user-secrets set "SeedAdmin:Password" "<password>"
```

### Testing strategy
Component tests are the default. Every new or changed frontend component gets Vitest tests next to it, covering what it renders, loading/empty/error states, user interactions, and the API calls it makes (path and params). Write E2E tests only when a component test can't prove the behaviour, i.e. it depends on the real backend or the full stack:
- auth, session and routing flows (sign-in, redirects, role-gated pages)
- backend contract and rules the UI relies on (status codes, validation errors, role checks, sort order, persistence across a reload)
- a critical end-to-end user journey that spans several pages

Don't duplicate in E2E what component tests already cover (rendering details, formatting, each UI state). When you finish a feature, write its component tests; only offer E2E tests if one of the cases above applies, and say which.

### Component tests (`frontend`, Vitest)
Vitest config is the `test` block in `vite.config.ts` (jsdom, files `src/**/*.test.{ts,tsx}`, setup in `src/test/setup.ts` which loads the jest-dom matchers). Tests sit next to the component (e.g. `src/users/UsersList.test.tsx`). Render anything that uses TanStack Query with `renderWithQueryClient` from `@/test/renderWithQueryClient` (a fresh client per test, no retries), and stub HTTP by `vi.mock('@/lib/api')`, keeping the real `ApiError`. Query by role and accessible name (`getByRole('table', { name: 'Tickets' })`), and drive interactions with `@testing-library/user-event`. `src/users/UsersList.test.tsx` and `src/tickets/TicketsList.test.tsx` are the references.

### E2E tests (`frontend`, Playwright)
`npm run test:e2e` runs the suite. How the E2E stack works and how to write tests lives in the `e2e-test-writer` sub-agent ([.claude/agents/e2e-test-writer.md](.claude/agents/e2e-test-writer.md)).

When E2E tests are warranted (see Testing strategy), use the `e2e-test-writer` sub-agent (Agent tool, `subagent_type: "e2e-test-writer"`) rather than writing specs yourself. Delegate directly if the user asked for E2E tests:
- In the prompt, name the feature, the pages/routes and backend endpoints involved, and only the scenarios that need the full stack. It starts with no context from this conversation.
- It only edits files under `frontend/e2e/`. When it reports an app bug or a missing accessibility hook (e.g. an input without a label), fix the app code yourself, then re-run it or the affected spec.
- Relay its results to the user: files changed, scenarios covered, the actual pass/fail summary, and any app issues or gaps it reported.

## Architecture

Two-project full-stack layout, no shared package boundary:
- `backend/TicketManagement.Api` — ASP.NET Core Web API. `Program.cs` is minimal-API style (no `Startup.cs`); DbContext registration, CORS policy, and any minimal endpoints (e.g. `/api/health`) are wired directly there. `Data/TicketManagementDbContext.cs` is the EF Core context (SQL Server provider). Minimal-API endpoint groups live in `Endpoints/` as `Map*Endpoints` extension methods called from `Program.cs`.
- `frontend` — React + Vite + TypeScript. Vite config uses Rolldown (`vite` v8 / `rolldown-vite` toolchain), not the standard Rollup-based Vite. API base URL is read from `VITE_API_BASE_URL` (see `.env`), not hardcoded — always use this when calling the backend from new frontend code.

### Auth
- Self-issued JWT (HMAC-SHA256). `Auth/TokenService.cs` issues tokens with `sub`, `email`, `name`, `role` claims. `Program.cs` validates them with `MapInboundClaims = false` and `RoleClaimType = "role"`, so use `RequireAuthorization(p => p.RequireRole(Roles.Admin))` for role-gated endpoints.
- Endpoints: `POST /api/auth/login`, `GET /api/auth/me` (`Endpoints/AuthEndpoints.cs`).
- Login rate limiting (`Auth/LoginRateLimiting.cs`: 10 req/min per IP, plus failed-attempt caps per email+IP and per email) is enabled only when the host environment is Production (`AddLoginRateLimiting(enabled: builder.Environment.IsProduction())`), i.e. `ASPNETCORE_ENVIRONMENT=Production` or the variable unset, since ASP.NET Core defaults to Production. The local launch profiles set `Development` (`http`/`https`) or `Testing` (`e2e`), where the policy is a no-op and failed logins aren't counted, so don't expect 429s locally. Any other environment name (e.g. `Staging`) also runs without rate limiting.
- `Models/User.cs`: `Role` is a string holding a `Roles` constant (`Models/Roles.cs`), `"Admin"` or `"Agent"`, stored as-is in the DB, the JWT and API responses. Emails are stored normalized via `User.NormalizeEmail`. The user row holds no credentials.
- `Models/Account.cs`: a user's sign-in methods live in the `Accounts` table (`Id`, `UserId` → `Users`, `Provider`, `PasswordHash`), unique per `(UserId, Provider)`. `Provider` is an `AuthProviders` constant: `"credential"` holds a password hashed with `PasswordHasher<User>`, while external providers like `"google"` (planned) leave `PasswordHash` null. Login looks up the user's `credential` account.
- Config: `Jwt:Issuer`, `Jwt:Audience`, `Jwt:ExpiryMinutes` are in `appsettings.json`. The dev-only `Jwt:SigningKey` is in `appsettings.Development.json`.
- Admin seeding is `Data/DbSeeder.cs`, called from `Program.cs` on every startup (there is no separate seed command): it applies pending migrations, then creates the admin from `SeedAdmin:*` if that email doesn't exist yet, and logs a warning and skips if unset. It never updates an existing user, so changing `SeedAdmin:Password` does not change an existing admin's password.
- Frontend: `src/lib/api.ts` exports `api`, an axios instance (base URL from `VITE_API_BASE_URL`) whose interceptors attach the Bearer token, sign the user out on a 401, and turn HTTP error responses into `ApiError` (message from the ProblemDetails `detail`/`title`). It also exports `errorMessage(error, fallback)`, which returns an `ApiError`'s message and the fallback for anything else (e.g. a network error). `src/auth/AuthProvider.tsx` + `useAuth()` (`src/auth/authContext.ts`) hold the session: the token is React state mirrored to `localStorage` under `auth.token`, the current user is the TanStack query `['auth', 'me']` (enabled only while a token exists), and `useAuth().login` is a `useMutation` result (`login.mutate({ email, password })`, `login.isPending`, `login.error`) that seeds `['auth', 'me']` on success. `logout()` clears the token and the whole query cache. `src/auth/LoginForm.tsx` is rendered by `pages/LoginPage.tsx`.

### Tickets and inbound email
- `Models/Ticket.cs` (subject, `Status` = a `TicketStatuses` value: the public `Open`/`Resolved`/`Closed` (`TicketStatuses.All`) or the AI-internal `New`/`Processing` (`TicketStatuses.Internal`, see Ticket processing below), nullable `Category` = a `TicketCategories` value, `Source` = a `TicketSources` value, submitter email/name) has many `Models/TicketMessage.cs` (sender, plain-text `Body`, `ExternalMessageId`, `AttachmentNames` stored as a JSON column). Internal statuses never reach the API or UI: every endpoint in `TicketEndpoints.cs` queries through `VisibleTickets(db)`, so a `New`/`Processing` ticket is missing from the list and returns 404 from detail and the update endpoints until the AI has finished with it, and the status filter and `PUT .../status` accept only `TicketStatuses.All`. The frontend `TicketStatus` type therefore has only the three public values. `GET /api/tickets` (`Endpoints/TicketEndpoints.cs`, any signed-in user) returns `{ items, page, pageSize, totalCount }` with `page` (default 1) and `pageSize` (default 25, max 100) query params, sorted by `sortBy` (`id`, `subject`, `submitter` = name falling back to email, `status`, `category`, `assignee` = display name with unassigned first ascending, `createdAt`; default `createdAt`) and `sortDir` (`asc`/`desc`, default `desc`), with `Id` in the same direction as the tiebreak. Optional `status` (a `TicketStatuses` value), `category` (a `TicketCategories` value, or `uncategorized` for a null category) and `assignee` (a user id, or `unassigned`) filters narrow both `items` and `totalCount`, as does `search` (trimmed, max 200 chars): a substring match on subject, submitter name or submitter email, plus an exact ticket id when the term is a number like `42` or `#42`. All of these match case-insensitively, and unknown values return a 400 validation problem. Dates are stored as UTC but read back from SQL Server as `DateTimeKind.Unspecified`, so the DTO projection wraps them in `DateTime.SpecifyKind(..., Utc)` to serialize with a `Z`. The frontend `/tickets` page (`pages/TicketsPage.tsx`, `tickets/TicketsList.tsx`) shows them in a paged table built with TanStack Table v9 (`@tanstack/react-table`: `useTable`, `tableFeatures({ rowSortingFeature, columnFilteringFeature, globalFilteringFeature })`, not v8's `useReactTable`). It uses `manualSorting` and `manualFiltering`: clicking a header, picking a Status/Category/Assignee filter (shadcn `NativeSelect`s above the table, wired to `column.setFilterValue`) or typing in the search box (the table's `globalFilter`, set 300 ms after typing pauses) only updates the table state. That state goes into the query key and API params, and changing it resets to page 1. Each subject links to `/tickets/:id` (`pages/TicketDetailPage.tsx`, `tickets/TicketDetail.tsx`, query key `['tickets', 'detail', id]`), a read-only view of the ticket's fields and message thread backed by `GET /api/tickets/{id}` (any signed-in user; 404 ProblemDetails `Ticket not found.`; messages oldest first, plain-text bodies shown with line breaks kept). Tickets have an optional assignee (`Ticket.AssigneeId` → `Users`, `SET NULL` on delete). An assignee is always an individual user (any admin or agent), never a role: the list's Assignee filter offers "All assignees", "Unassigned", then each user by display name, and the detail picker offers "Unassigned" plus each active user. The detail DTO includes `assignee: { id, displayName, email } | null`, and `PUT /api/tickets/{id}/assignee` with `{ userId }` (`null` unassigns) is admin-only. It accepts only active, non-deleted users (otherwise 400 on `userId`) and returns the updated detail. List items carry the same `assignee` object. `GET /api/users/assignees` (any signed-in user, unlike the admin-only `GET /api/users`) returns `{ id, displayName, isActive }` for every non-deleted user; the frontend reads it through `tickets/useAssigneeOptions.ts` (query key `['users', 'assignees']`) for both the list's Assignee filter (deactivated users included, marked "(inactive)") and the detail page's picker (active users only). On the page, `tickets/TicketAssignee.tsx` is a picker for admins and plain text for agents; the page passes `canAssign` from `useAuth()`. The detail page's child components (`TicketDetailHeading` for the id, subject, submitter, source and dates, `TicketProperties` for the sidebar that holds `TicketStatusSelect`, `TicketCategorySelect` and `TicketAssignee`, plus `TicketReplyForm`) take the whole `ticket` (`TicketDetailData`) rather than an id plus separate fields; their tests build one with `makeTicket(overrides)` from `@/test/ticketFixtures`. `TicketThread` (the message list) takes `ticket` too. Soft-deleting a user (`DELETE /api/users/{id}`) unassigns their tickets in the same save, because the user query filter would otherwise hide the assignee. Any signed-in user (agents resolve tickets) can change status and category: `PUT /api/tickets/{id}/status` with `{ status }` (any `TicketStatuses` value, matched case-insensitively; any status may follow any other, so tickets can be reopened) and `PUT /api/tickets/{id}/category` with `{ category }` (a `TicketCategories` value, or `null` to clear it). Unknown values return a 400 validation problem, and both return the updated detail. On the page they are `tickets/TicketStatusSelect.tsx` and `tickets/TicketCategorySelect.tsx`, which save on change. All three ticket field updates go through `tickets/useUpdateTicket.ts` (`useUpdateTicket(ticketId, 'status' | 'category' | 'assignee')`), which PUTs to `/api/tickets/{id}/{field}`, puts the returned ticket into `['tickets', 'detail', id]` and invalidates the list queries. Agent replies are `TicketMessage` rows too: each message has a `Direction` (`MessageDirections`: `inbound` from the customer, `outbound` a reply) and, for replies, an `AuthorId` (→ `Users`, `SET NULL`) plus a snapshot of the author's email and display name in `SenderEmail`/`SenderName`. `POST /api/tickets/{id}/replies` with `{ body }` (any signed-in user; trimmed, 1–10,000 chars, otherwise 400 on `body`) appends a reply, bumps `UpdatedAt` and returns 201 with the updated detail; it doesn't change the status. Replies are emailed to the submitter in the background (see Outbound email below); the response doesn't wait for the email. The detail DTO's messages carry `direction` and `deliveryStatus`; the thread is `tickets/TicketThread.tsx` (takes `ticket`, no data fetching), which shows customer messages as left-aligned mint bubbles and replies as right-aligned pine bubbles with a "Reply" badge, and `tickets/ReplyDeliveryStatus.tsx` ("Sending email…", "Emailed", "Email failed" with a Resend button via `tickets/useResendReply.ts`, or "Not emailed") in the same oldest-first list, and `tickets/TicketReplyForm.tsx` (via `tickets/useAddReply.ts`, which updates the cache like `useUpdateTicket`) sits below it. Status badge variants and category labels shared by both views, plus `formatDate` (used by the detail header and thread) and `ticketDetailColumns` (the detail page's two-column grid, shared with `tickets/TicketDetailSkeleton.tsx`), live in `tickets/ticketDisplay.ts`.
- Resolution tracking and dashboard: `Ticket.ResolvedAt` and `Ticket.ResolvedByAi` are set by the auto-resolver (`ResolvedByAi = true`) or by `PUT .../status` the first time a ticket moves to Resolved or Closed (`ResolvedByAi = false`). Moving between Resolved and Closed keeps them, and reopening (`Open`) clears both. They are not in the ticket DTOs. `GET /api/dashboard` (`Endpoints/DashboardEndpoints.cs`, any signed-in user) returns `{ totalTickets, openTickets, resolvedByAi, averageResolutionSeconds }` (`averageResolutionSeconds` = mean `CreatedAt → ResolvedAt`, null when nothing is resolved). Both dashboard endpoints are thin wrappers over SQL Server inline table-valued functions, `dbo.GetDashboardStats()` and `dbo.GetTicketsPerDay(@UtcOffsetMinutes, @Days)` (at most 100 days), created in the `AddDashboardFunctions` migration and read with `Database.SqlQuery<TDto>`. The functions repeat the `VisibleTickets` rule (skip `New`/`Processing`) in SQL, so change both together. To change a function, add a new migration with `CREATE OR ALTER FUNCTION`; don't edit the applied one. The home page (`pages/HomePage.tsx`) greets the user by time of day ("Good morning, {name}", `dashboard/greeting.ts`). It shows the stats in one mint panel via `dashboard/DashboardStats.tsx`, which also prints "N tickets are waiting for a reply." and computes the AI-resolved percentage from the counts. Each stat is a `role="group"` labelled with its name, and its value is the group's only `<p>`. Its query key `['tickets', 'stats']` is refreshed by the existing ticket mutations' invalidation. Below it, `dashboard/TicketsPerDayChart.tsx` (shadcn `chart`, i.e. Recharts) plots `GET /api/dashboard/tickets-per-day?utcOffsetMinutes=` (the browser's offset; ±840 max, else 400), which returns `[{ date: 'YYYY-MM-DD', count }]` for the last 30 days, today included, oldest first, zero-filled, bucketed by `CreatedAt` in that offset. Recharts renders nothing in jsdom, so its tests assert on the screen-reader table that mirrors the chart.
- `POST /api/inbound-email` (`Endpoints/InboundEmailEndpoints.cs`) turns a received email into a new ticket with one message: `New` and queued for classification and auto-resolve when `Gemini:ApiKey` is set, otherwise `Open` straight away with nothing queued (so Testing/E2E tickets are `Open` immediately). It takes a provider-agnostic JSON body (`messageId`, `from: { email, name }`, `subject`, `text`, `html`, `attachments: [{ fileName }]`); a provider webhook or mailbox poller maps its own payload onto this shape. It is called machine-to-machine, so instead of a JWT it requires the `X-Inbound-Email-Secret` header to equal `InboundEmail:Secret` (dev/test values are in `appsettings.Development.json` / `appsettings.Testing.json`; set `InboundEmail__Secret` elsewhere, or the endpoint returns 503).
- Behaviour: returns 201 `{ ticketId, duplicate: false }`; a repeated `messageId` returns 200 with the existing ticket and `duplicate: true` (webhooks retry). `text` is preferred, with `html` converted to plain text by `Email/HtmlText.cs` as the fallback, and raw HTML is never stored. Attachment contents are not stored, only names. Replies are not threaded: every email is a new ticket. `TicketManagement.Api.http` has a sample request.
- SendGrid Inbound Parse: `POST /api/inbound-email/sendgrid` (same file) is SendGrid's adapter onto the same ticket-creation code. SendGrid can't send custom headers, so the same `InboundEmail:Secret` comes in the `?secret=` query parameter of the Destination URL configured in SendGrid (Settings → Inbound Parse). It reads SendGrid's default parsed `multipart/form-data` body, so leave "POST the raw, full MIME message" unchecked. Field mapping: `from` (`Name <address>`, falling back to `envelope.from`), `subject`, `text`, `html`, the `Message-ID` line of the raw `headers` field, and file names from `attachment-info` (the file parts are ignored). Its body limit is 30 MB (SendGrid's maximum) instead of the JSON endpoint's 2 MB, because the files are posted too. SendGrid retries non-2xx responses. Locally, SendGrid reaches it through the ngrok tunnel to the Vite dev server, which proxies `/api` to the backend.
- Ticket processing (`Ai/`): classification and knowledge-base auto-resolve run as two independent pipelines, each an in-memory bounded `Channel<int>` queue (never blocks) read by its own `BackgroundService`, one ticket at a time. After saving a `New` ticket, the inbound-email endpoint enqueues its id on both queues and returns straight away. Neither pipeline waits for or depends on the other.
- Auto-classification: `TicketClassificationQueue` → `TicketClassificationWorker`. It sends the subject and first inbound message to `IAiService.ClassifyTicketAsync` and writes the result with a conditional `ExecuteUpdateAsync` (`Category == null`), so it never overwrites a category an agent set. It doesn't touch the status. Failures are logged and leave the ticket uncategorized. Ids still queued when the app stops are lost. With no `Gemini:ApiKey` the worker logs one warning and skips.
- Auto-resolve: `TicketAutoResolveQueue` → `TicketAutoResolveWorker`. Every status change is a conditional `ExecuteUpdateAsync`:
  - It claims the ticket (`New → Processing`), skipping it if it's no longer `New`.
  - It calls `IAiService.TryResolveTicketAsync` with the text from `Ai/KnowledgeBase.cs`. That is a singleton reading `KnowledgeBase:Path` (default `knowledge-base.md` in the content root, copied to the build output by the csproj) once and caching it, so edits need a restart.
  - The model answers only from the knowledge base and returns `{ canResolve, reply }`. It must refuse (`canResolve: false`) when the knowledge base's escalation rules apply (legal threats, refunds outside 30 days, chargebacks, account security, low confidence) or the answer isn't covered.
  - The reply is posted as a real user, indistinguishable from a manual reply: `AuthorId`, sender email and display name are set, and it's signed with that user's name. That user is the active user at `AutoResolve:ReplyAsEmail` (optional config) or else the earliest-created active admin, normally the seeded one. With no such user the ticket goes to `Open`. On a reply, one transaction sets `Processing → Resolved` and adds that outbound `TicketMessage`. Like agent replies, it is then emailed to the submitter.
  - Otherwise the ticket goes `Processing → Open`: escalated, the AI call failed, missing knowledge base, or the app stopping mid-call. That reset runs in a `finally` with no cancellation token, so a claimed ticket is never left in `Processing`.
  - There is no recovery on startup: ids still queued when the app stops (or dropped because the queue is full) are lost, and those tickets stay `New`, hidden from the UI. With no `Gemini:ApiKey` the worker logs one warning and processes nothing.
- Outbound email (`Email/`): replies (manual and auto-resolve) are emailed to the ticket's submitter through SendGrid (`SendGrid` + `SendGrid.Extensions.DependencyInjection` packages, `ISendGridClient` registered with `AddSendGrid` in `Program.cs`). Config is `Email/SendGridOptions.cs`: `SendGrid:ApiKey` (secret), `SendGrid:FromEmail` (`help@pranavsupport.online` in `appsettings.json`; must be a verified sender or on an authenticated domain in SendGrid) and `SendGrid:FromName`. Without an API key (so in Testing/E2E) replies get a null `DeliveryStatus` and nothing is emailed or enqueued.
  - Each reply's `TicketMessage.DeliveryStatus` is a `MessageDeliveryStatuses` value (`pending`, `sent`, `failed`; null for inbound messages and replies that aren't emailed), plus `DeliveryAttempts`, `SentAt`, `DeliveryError` and SendGrid's `ProviderMessageId` (X-Message-Id). Only `deliveryStatus` is in the DTO.
  - Saving a reply as `pending` enqueues its id on `ReplyEmailQueue` (bounded `Channel<int>`), read by `ReplyEmailWorker` one at a time. It sends a plain-text email "Re: {subject}", with `In-Reply-To`/`References` set to the ticket's first inbound `ExternalMessageId` so it threads in the customer's mail client. Network errors, 429 and 5xx are retried (3 attempts, 2 s then 10 s apart); other errors fail at once. Then it's `sent` or `failed` (the error is logged and stored). The reply's body is kept either way.
  - Unlike the AI queues, nothing is lost on restart: on startup the worker first sends every reply still `pending` in the database. A crash between SendGrid accepting an email and saving `sent` re-sends it on restart (at-least-once).
  - `POST /api/tickets/{id}/replies/{messageId}/resend` (any signed-in user) moves a `failed` reply back to `pending` with a conditional update and enqueues it; 409 if the reply isn't `failed`, 404 if it isn't an outbound message on that ticket, 503 if SendGrid isn't configured. Returns the updated detail.
  - The detail page's query (`tickets/TicketDetail.tsx`) refetches every 3 s while any message is `pending`.
  - Customer replies to these emails go to `FromEmail`, which comes back in through Inbound Parse as a new ticket (threading is deferred).

### Error reporting (Sentry)
- Both projects report errors to Sentry only when a DSN is configured, so tests, Testing and E2E runs never report.
- Backend: `Sentry.AspNetCore`, enabled in `Program.cs` with `builder.WebHost.UseSentry()` only when `Sentry:Dsn` (or `SENTRY_DSN`) is set. The SDK refuses to start without a DSN, so don't call it unconditionally. Options are in the `Sentry` section of `appsettings.json`. It captures unhandled request exceptions and every `LogError`/`LogCritical` (`MinimumEventLevel: Error`), so the background workers' failures are reported through their existing `logger.LogError` calls. Log at `Warning` for expected, handled failures that shouldn't become Sentry issues. `SendDefaultPii` is false and `MaxRequestBodySize` is `None`, because request bodies carry customers' emails and messages.
- Frontend: `@sentry/react` v11, initialized by `initSentry()` (`src/lib/sentry.ts`) from `VITE_SENTRY_DSN` (in `.env.local`), with `environment` = the Vite mode. v11 collects request bodies, cookies, user info and GenAI prompts by default, so `dataCollection` turns those off explicitly (the Polish/Summarize buttons send ticket content to Gemini). Keep it that way when adding options. `main.tsx` passes `Sentry.reactErrorHandler()` to `createRoot`'s `onUncaughtError`/`onCaughtError`/`onRecoverableError` and wraps the app in `Sentry.ErrorBoundary`, whose fallback is `components/AppErrorFallback.tsx` (a Reload button). Handled API errors (shown with `ErrorAlert`) aren't reported from the frontend; the backend reports its own failures. Source maps aren't uploaded, so frontend stack traces show minified code in production builds.

### Configuration and secrets
- Environments come from `ASPNETCORE_ENVIRONMENT`: `Development` (launch profiles `http`/`https`), `Testing` (launch profile `e2e`, Playwright only), and `Production` (deployed, or the variable unset). Environment-dependent behaviour: OpenAPI is mapped only in Development, the database is dropped and recreated on startup only in Testing, and login rate limiting runs only in Production.
- Committed config: `appsettings.json` (JWT issuer/audience/expiry, CORS origins), `appsettings.Development.json` (LocalDB connection string `TicketManagementDb`, dev JWT signing key) and `appsettings.Testing.json` (`TicketManagementDb_E2E` connection string, test-only JWT signing key, E2E CORS origin).
- Secrets that must not be committed (admin seed credentials, a real `InboundEmail:Secret`, `SendGrid:ApiKey`) go in dotnet user-secrets (`secrets.json`, via `<UserSecretsId>` in the csproj), never in appsettings or a `.env` file. User-secrets load only in Development. The one deliberate exception is the E2E admin in `frontend/e2e/testUsers.ts`: it is committed because it only ever exists in the throwaway `TicketManagementDb_E2E`.
- `KnowledgeBase:Path` (optional, not secret) points the auto-resolver at a different knowledge-base file, resolved relative to the content root. The default `knowledge-base.md` is committed next to `Program.cs`. `AutoResolve:ReplyAsEmail` (optional, not secret) picks which user auto-resolve replies are sent as.
- `frontend/.env` is committed on purpose because it only holds the non-secret `VITE_API_BASE_URL`. Frontend secrets would go in a git-ignored `.env.local`. `frontend/.env.example` documents every variable; add new `VITE_*` variables there too.
- `.gitignore` also excludes `.claude/settings.local.json`.

### Cross-cutting conventions
- CORS in `Program.cs` is a single named policy whose origins come from `Cors:AllowedOrigins` (`appsettings.json`: the Vite dev origin `http://localhost:5173`; `appsettings.Testing.json`: `http://localhost:5174`). If a frontend port changes, update the matching setting, or the two won't be able to talk to each other. `appsettings.Development.json` overrides the list to add the dev ngrok origin; it repeats `http://localhost:5173` because configuration arrays merge by index.
- The Vite dev server allows `.ngrok-free.dev` hosts and proxies `/api` to `http://localhost:5280` (`server.proxy` in `vite.config.ts`), so one ngrok tunnel serves both the app and the API (including the SendGrid webhook). Setting `VITE_API_BASE_URL=` (empty) in `.env.local` makes the app call relative `/api/...` through that proxy.
- Server state goes through TanStack Query (`@tanstack/react-query` v5): read with `useQuery`, write with `useMutation`, and have every `queryFn`/`mutationFn` call the `api` axios instance (e.g. `api.get<T>(path).then((r) => r.data)`). Don't fetch in `useEffect`, and don't call `fetch` or plain `axios` directly. The single `QueryClient` (in `src/lib/queryClient.ts`, provided in `main.tsx` outside `BrowserRouter`/`AuthProvider`) sets a 30s `staleTime` and skips retries for 4xx `ApiError`s. After a mutation, invalidate or `setQueryData` on the affected query keys.
- Types for API data (request/response shapes and their enums) live in `src/types/`, one file per domain: `ticket.ts` (`TicketDetailData`, `TicketMessage`, `TicketListItem`, `TicketStatus`, ...), `user.ts` (`UserListItem`, `AssigneeOption`) and `auth.ts` (`Role`, `AuthUser`, `LoginResponse`, `LoginCredentials`). Import them with `import type { … } from '@/types/<domain>'`; don't declare them in component or hook files. Types that belong to one piece of code stay next to it, e.g. a form's `z.infer` values type and `AuthContextValue`.
- Error banners use `<ErrorAlert>` (`src/components/ErrorAlert.tsx`, a destructive shadcn `Alert` with an icon) instead of hand-writing the `Alert` markup. For a failed query or mutation, pass it `errorMessage(query.error, 'Could not load …')` from `@/lib/api`. Inline field-level errors (e.g. under the ticket status/category/assignee selects) use the same `errorMessage` helper but stay a small `role="alert"` paragraph.
- Forms use React Hook Form (`react-hook-form` v7) with Zod (`zod` v4) schemas via `zodResolver` from `@hookform/resolvers/zod`: define a schema next to the form, type values with `z.infer<typeof schema>`, bind inputs with `register`, show `formState.errors` per field, and set `noValidate` on the `<form>` so Zod, not the browser, does the validation. The submit handler passes the parsed values to a `useMutation`. `src/auth/LoginForm.tsx` is the reference.
- Styling is Tailwind CSS v4 via the `@tailwindcss/vite` plugin (no `tailwind.config.js`, no PostCSS config), with shadcn/ui (`components.json`: `base-nova` style, i.e. Base UI primitives, neutral base color, lucide icons). Add components with `npx shadcn@latest add <name>` (they land in `src/components/ui/`); `cn()` comes from `@/lib/utils`. Imports use the `@/` alias for `src/` (set in `tsconfig.json`, `tsconfig.app.json` and `vite.config.ts`). `src/index.css` holds the shadcn theme tokens (`--background`, `--primary`, ...) and base styles for plain elements: `h1` is `font-heading text-3xl font-semibold tracking-tight`, `h2` is `font-heading text-lg font-semibold tracking-tight`, and `dt` is `text-muted-foreground`. Don't repeat those classes on the elements; add only per-use extras like margins. Put a style in the base layer only when every use of that element shares it (shadcn components override it with their own utilities, e.g. dialog titles render an `h2`); prefer the semantic token utilities (`bg-background`, `text-muted-foreground`, `bg-primary`) over raw palette colors, style with utility classes in `className`, and don't add custom CSS files or class names. Dark mode follows the OS: the `dark` variant and the dark token set are both keyed to `prefers-color-scheme: dark` (not shadcn's default `.dark` class), and `<html>` has `scheme-light-dark` in `index.html`.
- Visual design ("Calm studio"): the tokens in `src/index.css` are pine (`--primary` `#1F4D3A`), mint (`--muted`/`--secondary`/`--accent` `#E8F2EC`), green-tinted ink, and `--sun` (`bg-sun`/`text-sun`). Sun is reserved for AI output: the AI-resolved stats, the Summarize button and the summary panel. Fonts come from Fontsource: Bricolage Grotesque for headings, the brand and big numbers (`font-heading`), and Figtree for everything else (`font-sans`). Separate sections with mint panels (`rounded-2xl bg-muted`) rather than borders and shadows, and keep page content inside the `max-w-6xl` column that `AppLayout` sets.
  - Data tables go inside a div with the `tablePanel` classes from `components/tablePanel.ts`.
  - People are shown as `components/UserAvatar.tsx` beside their name. The avatar draws the initials (from `lib/initials.ts`) with CSS `content`, so they don't appear in the text of a table cell.
  - The ticket thread is a conversation: customer messages are left-aligned mint bubbles and replies are right-aligned pine bubbles.
- Routing uses React Router v7 in declarative mode (imported from `react-router-dom`): `<BrowserRouter>` wraps `AuthProvider` in `main.tsx`, and the route tree lives in `App.tsx`. Protected routes nest under the `auth/RequireAuth.tsx` layout route (redirects to `/login` when there's no user, so `logout()` needs no explicit navigate), then `components/AppLayout.tsx` (nav bar + `<Outlet />`). Role-gated pages nest further under `<RequireRole role="Admin" />` (`auth/RequireRole.tsx`), which redirects users without that role to `/` (e.g. the admin-only `/users` page). This only hides UI; the matching backend endpoints must still enforce the role. Pages go in `src/pages/`.
- Docker is deferred to a later phase; local dev currently runs both projects directly (no docker-compose yet), against SQL Server LocalDB (`(localdb)\mssqllocaldb`) on the host, not a container.
- A running backend locks `bin/Debug/.../TicketManagement.Api.exe`, so stop it before `dotnet build` / `dotnet run` or the build fails with MSB3027. (The E2E backend avoids this by building with `-p:OutDir=bin/e2e/`.)
- Interim AI exception: the reply form's "Polish" button (`tickets/usePolishReply.ts` → `polishReply` in `src/lib/ai.ts`) calls Gemini straight from the browser via the Vercel AI SDK (`ai` + `@ai-sdk/google`), with the key in `VITE_GEMINI_API_KEY` (git-ignored `.env.local`). That key is public in the bundle, so this is local-demo only, and it's the one `mutationFn` that doesn't use `api`. It replaces the draft and never sends it, greets the submitter by first name ("Hello Jane,", or "Hello," without a name), adds emojis where the tone allows, and signs it "Best regards," plus the signed-in user's display name (`agentName`, passed down from `TicketDetailPage`). The "Summarize" button above the thread (`tickets/TicketSummary.tsx` → `tickets/useSummarizeTicket.ts` → `summarizeTicket` in `src/lib/ai.ts`) works the same way: a mutation, not a query, so each click regenerates the summary from the ticket's subject, status and messages, and nothing is stored. Tests mock `@/lib/ai`. Move it behind the backend `IAiService` in Phase 3.
- Backend AI goes through `Ai/IAiService.cs`, implemented by `Ai/ChatAiService.cs` on Microsoft.Extensions.AI's `IChatClient`. `Program.cs` registers that client with `AddChatClient` as Gemini via Google's `Google.GenAI` SDK (`AsIChatClient(model)`), configured by `Gemini:ApiKey` (secret) and `Gemini:Model` (`Ai/GeminiOptions.cs`, default `gemini-3.5-flash`). Swapping providers means changing only that registration. Structured answers use `ChatResponseFormat.ForJsonSchema` with a schema built from the model constants (e.g. `TicketCategories.All`). Add new AI features as `IAiService` methods; don't call a provider SDK or `IChatClient` from endpoints.

## Using Context7

Use the Context7 MCP tools to fetch current documentation whenever working with a library, framework, SDK, API, CLI tool, or cloud service in this repo (ASP.NET Core, EF Core, React, Vite, React Router, SendGrid, Claude/Gemini APIs, etc.) — including for setup, config, version-specific API syntax, and migration questions. Prefer this over relying on training data or web search for library docs, since API surfaces (especially fast-moving ones like EF Core and ASP.NET Core minimal APIs) change between versions.

1. Call `resolve-library-id` with the library name first, unless an exact `/org/project` ID is already known.
2. Pick the best-matching library ID (exact name match, relevant description, higher snippet count, High/Medium source reputation, higher benchmark score).
3. Call `query-docs` with that library ID and a specific, single-concept question. Split multi-concept questions into separate calls.
4. Answer from the fetched docs rather than assuming API shape from memory.

Do not use Context7 for refactoring, debugging business logic, or general programming questions unrelated to a specific library's API.
